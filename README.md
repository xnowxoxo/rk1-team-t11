# РК1, трек 11: гистограмма + сортировка подсчётом

Массив из 5·10⁸ целых чисел. Нужно построить гистограмму и по ней отсортировать массив.
MPI-версия работает со значениями от 0 до 1023, OpenMP-версия — от 0 до 255.

Команда:
- Шамиль Н. - MPI
- Аюпов И. - OpenMP

## Файлы

```
src/      common.h  seq.c  mpi.c                 MPI-часть и её эталон
          hist.h  seq_omp.c  omp.c               OpenMP-часть и её эталон
          placement_test.c                       побочный тест к анализу OpenMP
slurm/    mpi.sbatch  omp.sbatch  placement_test.sbatch
scripts/  analyze.py                             графики MPI
          plot_omp.py                            графики и таблица OpenMP
logs/     логи Slurm без правок (omp_2487.out, placement_test_2489.out — OpenMP)
plots/    speedup.png  efficiency.png            MPI
          omp_speedup.png  omp_efficiency.png  omp_metrics.md   OpenMP
```

В `common.h` то, что общее для seq и mpi: генерация массива и проверка результата.
В `hist.h` то, что общее для seq_omp и omp: генерация массива (splitmix64 от индекса, одинаковая при любом числе потоков)
и функция подсчёта `count()`. Её вызывают и эталон, и каждый поток OpenMP, поэтому T1 и T(p) измеряют один и тот же машинный код.

## Проверка

seq считает контрольную сумму отсортированного массива Σ sorted[i]·(i+1) и записывает её в `ref_500000000.txt`. mpi считает такую же сумму и сравнивает с эталоном. Если совпало — `OK`.

seq_omp и omp после замера заново последовательно пересчитывают гистограмму, она должна совпасть.
Отсортированный массив должен быть неубывающим, а число каждого значения в нём — совпасть с гистограммой.

Вывод: `version;p;time_s;CHECK`, строки с `#` — дополнительная информация.

## MPI

1. rank 0 раздаёт массив через `MPI_Scatterv`. Каждому по n/p элементов, первые n mod p процессов получают на один больше.
2. Каждый процесс строит свою гистограмму.
3. `MPI_Reduce` складывает гистограммы на rank 0, потом `MPI_Bcast` отдаёт итоговую всем.
4. Каждый процесс по общей гистограмме заполняет свой кусок отсортированного массива (те же позиции, что и в Scatterv).

Время считается от Scatterv до конца сортировки. В строке `#detail` время каждого этапа.

## OpenMP

Два варианта гистограммы, выбираются аргументом: `./bin/omp atomic` и `./bin/omp local`.

- **atomic**: `parallel for schedule(static)`, каждый инкремент — `#pragma omp atomic` на общую гистограмму из 256 счётчиков.
- **local**: каждый поток считает свой блок массива (те же границы, что у `schedule(static)`) в собственную гистограмму
  функцией `count()`, затем один раз прибавляет её к общей под `critical` (256 сложений на поток).
  В горячем цикле нет атомарных операций и общих записей.
- **сортировка (fill)**: `parallel for schedule(static)` по 256 значениям. Значение b пишет `out[start[b] .. start[b+1])`,
  диапазоны не пересекаются, гонок нет. Префиксная сумма по 256 элементам остаётся последовательной.
- **first touch**: массивы инициализируются параллельно с тем же `schedule(static)`, поэтому страницы каждого потока
  лежат на его NUMA-узле. Отсортированный массив заполняется −1, а не 0: иначе gcc заменяет `malloc` + обнуление на `calloc`,
  страницы остаются нетронутыми, и эталон платил бы за их выделение внутри замера.

Время считается от начала гистограммы до конца сортировки, генерация данных и проверка не входят.
В строке `# hist=… fill=…` время двух этапов. Каждое значение в таблицах — минимум из 3 запусков.

## Как запустить на PARAM BILIM

```bash
# на bilim-master
module load intel/mpi/2021.14
make
mkdir -p logs
sbatch slurm/mpi.sbatch
sbatch slurm/omp.sbatch      # сам собирает bin/seq_omp и bin/omp, ~3 минуты на pbcn02
squeue -u $USER

# после окончания
python3 scripts/analyze.py
python3.11 scripts/plot_omp.py   # нужен matplotlib (есть в python3.11 на bilim-master)
```

Для быстрой проверки на маленьком массиве: `HIST_N=1000000 ./bin/seq` и так же для остальных (кроме OpenMP-части: там размер задан в `hist.h`).

Ручной запуск OpenMP: `./bin/seq_omp`, `OMP_NUM_THREADS=8 ./bin/omp atomic`, `OMP_NUM_THREADS=8 ./bin/omp local`.

## Узел

OpenMP-замеры: pbcn02, 2 × Intel Xeon Gold 6336Y @ 2.40 GHz, 2 сокета × 24 ядра, HT = 2, 2 NUMA-узла; gcc 8.5.0.
Запуск с `--exclusive`, `OMP_PLACES=cores`, `OMP_PROC_BIND=spread`, каждый поток на своём физическом ядре.
Из-за нумерации ядер на этом узле `spread` при p = 2, 4, 8 и 24 ставит все потоки на сокет 0,
при p = 16 — 8 + 8, при p = 32 — 24 + 8.

MPI: заполнить `mpirun --version`.
